## 第 4 章 系统设计

### 4.1 系统架构设计

#### 4.1.1 整体架构

本系统采用前后端分离的三层架构设计，将系统划分为表示层、业务层和数据层，各层之间通过清晰的接口进行通信。

**（1）表示层**

表示层基于 Vue 3 和 Vant 4 移动端组件库构建，负责用户界面的展示和交互。该层通过 Vue Router 实现前端路由管理，通过 Pinia 进行全局状态管理，通过 Axios 封装的 API 客户端与后端进行数据交换。表示层不直接处理业务逻辑，仅负责数据展示和用户操作的捕获。

**（2）业务层**

业务层基于 FastAPI 框架构建，包含所有核心业务逻辑。该层通过路由模块（Routes）接收前端请求，通过服务模块（Services）执行具体的业务处理，包括：

- `llm_service`：大语言模型调用服务
- `rag_service`：检索增强生成服务
- `vector_service`：向量数据库操作和嵌入服务
- `vision_service`：多模态视觉识别服务

业务层通过依赖注入（Dependency Injection）模式管理数据库会话和认证状态，确保请求处理的独立性和安全性。

**（3）数据层**

数据层由两个数据库组成：

- **MySQL**：存储所有结构化业务数据，包括用户信息、健康档案、对话记录、食谱数据等
- **PostgreSQL + pgvector**：存储向量化知识数据，支持语义相似度搜索

两个数据库各司其职，通过 SQLAlchemy ORM 框架进行数据访问抽象。

#### 4.1.2 技术选型

**（1）前端技术栈选择依据**

Vue 3 作为渐进式 JavaScript 框架，具有组件化开发、响应式数据绑定和 Composition API 等特性，适合构建复杂的单页应用（SPA）。Vant 4 是轻量级移动端组件库，提供 60 余种高质量组件，开箱即用。Vite 作为构建工具，基于 ES Module 原生支持，提供极快的热模块替换（HMR）和冷启动速度。

**（2）后端技术栈选择依据**

FastAPI 是现代、高性能的 Python Web 框架，基于 ASGI 协议和 Starlette，原生支持异步编程和自动 API 文档生成。Pydantic 提供强大的数据验证和序列化能力，与 FastAPI 深度集成。SQLAlchemy 是 Python 中最成熟的 ORM 框架，支持多种数据库和复杂查询。

**（3）数据库选型分析**

MySQL 作为关系型数据库，具有成熟稳定、社区活跃、生态完善的特点，适合存储结构化业务数据。PostgreSQL 配合 pgvector 扩展，提供了向量数据存储和语义搜索能力，无需额外部署独立的向量数据库服务，降低了系统部署复杂度。双数据库方案在保证各自最优性能的同时，实现了数据的合理分层管理。

#### 4.1.3 系统部署架构

系统部署架构包含以下组件：

- **前端服务**：通过 Vite 构建静态资源，部署到 Nginx 或 CDN
- **后端服务**：通过 Uvicorn 或 Gunicorn 运行 FastAPI 应用
- **MySQL 数据库**：存储业务数据，运行在本地或远程服务器
- **PostgreSQL 数据库**：存储向量数据，需安装 pgvector 扩展
- **外部 API 服务**：豆包大模型 API、阿里云 DashScope API（Embedding 和 VLM）

### 4.2 功能模块设计

#### 4.2.1 用户认证模块

【图4.3 用户注册登录流程图】

（流程图应展示用户注册和登录的完整流程，包括数据校验、密码加密、JWT 签发等步骤）

**（1）注册流程设计**

用户注册流程如下：

1. 用户提交注册信息（用户名/邮箱/手机号、密码）
2. 后端通过 Pydantic 模型验证输入数据的有效性
3. 校验至少提供一种联系方式（用户名、邮箱或手机号）
4. 检查用户名和邮箱是否已存在，防止重复注册
5. 使用 bcrypt 算法对密码进行哈希加密
6. 将用户数据写入 MySQL 的 users 表
7. 返回注册成功的响应

**（2）登录流程设计**

用户登录流程如下：

1. 用户提交登录凭据（用户名/邮箱/手机号、密码）
2. 后端根据提供的凭据类型在 users 表中查找用户记录
3. 使用 bcrypt.checkpw 验证密码是否正确
4. 验证通过后，生成 JWT Token，包含用户 ID 和过期时间
5. 返回包含 Token 和用户信息的响应

**（3）JWT Token 机制**

系统使用 JWT（JSON Web Token）进行身份认证。Token 结构包含：

- **Header**：声明签名算法（HS256）
- **Payload**：包含用户 ID（sub 字段）和过期时间（exp 字段）
- **Signature**：使用配置的密钥对 Header 和 Payload 进行签名

Token 默认有效期为 24 小时。所有需要认证的接口通过 FastAPI 的依赖注入机制验证 Token 的有效性，未认证或过期的请求将被拒绝。

#### 4.2.2 营养咨询模块

【图4.4 营养咨询对话流程图】

（流程图应展示对话交互流程，包括上下文获取、LLM 调用、结果保存等步骤）

**（1）对话交互流程**

营养咨询模块的交互流程设计如下：

1. 用户输入自然语言问题
2. 系统获取当前用户最近的 N 轮对话历史作为上下文
3. 将系统提示词、历史对话和当前问题组装为消息列表
4. 调用豆包大模型 API 生成回答
5. 将用户问题和系统回答保存到 chat_records 表
6. 将回答返回给前端展示

**（2）上下文管理机制**

系统采用最近 N 轮对话作为上下文的策略。每次对话请求时，系统从 chat_records 表中按时间倒序查询该用户最近的对话记录，将其转换为大语言模型的消息格式（包含 user 和 assistant 角色），与当前问题一起发送给模型。该策略确保模型能够理解对话的上下文，提供连贯的回答。

**（3）历史记录存储方案**

所有对话记录存储在 MySQL 的 chat_records 表中，每条记录包含用户 ID、问题内容、回答内容和创建时间。用户可通过对话历史接口按时间倒序浏览自己的咨询记录。

**（1）RAG 推荐流程设计**

个性化食谱推荐流程如下：

1. 用户提交偏好信息和已有食材列表
2. 系统获取用户的健康档案、饮食偏好和健康目标信息

5. 将推荐结果返回给用户

系统根据当前月份自动判断季节：

| 季节 | 月份 |
|------|------|
| 春季 | 3-5 月 |
| 夏季 | 6-8 月 |
| 秋季 | 9-11 月 |
| 冬季 | 12-2 月 |

通过查询 ingredients 表中的 season 字段，系统获取当季适宜食用的食材列表，为用户提供季节性饮食建议。

**（1）多模态识别接口设计**

系统提供两种食材识别方式：

- **文件上传**：通过 multipart/form-data 接收图片文件，保存到服务器 uploads 目录，调用 Qwen-VL 模型识别

**（2）识别结果处理流程**

1. 用户上传图片
2. 系统调用 Qwen-VL 多模态视觉模型分析图片内容
3. 模型返回识别到的食材列表
4. 系统将识别结果保存到 food_recognition_records 表
5. 返回识别结果给用户，可直接用于食谱推荐

#### 4.2.5 健康管理模块

健康管理模块包含三个子模块：健康档案、饮食偏好和健康目标。

**（1）健康档案数据结构**

健康档案存储在 user_health_profile 表中，包含用户的年龄、性别、身高、体重、活动水平和健康状况描述。系统根据身高（cm）和体重（kg）自动计算 BMI 值，计算公式为：

BMI = 体重(kg) / [身高(m)]²

**（2）BMI 自动计算逻辑**

BMI 计算在后端响应时进行，无需在前端重复计算。当查询健康档案时，系统读取身高和体重数据，在响应模型中动态计算 BMI 并包含在返回结果中。

**（3）偏好与目标关联设计**

饮食偏好（user_diet_preferences）和健康目标（user_health_goals）均通过 user_id 外键与 users 表关联。每个用户可拥有多条健康目标记录，但仅拥有一条饮食偏好记录（通过唯一索引保证）。

#### 4.2.6 知识库管理模块

【图4.7 文档解析与入库流程图】

（流程图应展示文档解析与入库的完整流程，包括文件上传、文档解析、文本分块、向量化、存储等步骤）

**（1）文档解析流水线设计**

文档解析流水线包含以下步骤：

1. **文件上传验证**：检查文件格式（PDF/Word/TXT/Markdown）和大小（限制 50MB）
2. **文档解析**：根据文件类型选择对应的解析方法
   - PDF：使用 PyPDF2 逐页提取文本
   - Word：使用 python-docx 提取段落文本
   - TXT：按 UTF-8 编码读取纯文本
   - Markdown：提取文本内容
3. **文本分块**：按照指定的分块方法将文本分割为多个片段
4. **向量化**：通过 DashScope text-embedding-v4 模型将文本转换为 1024 维向量
5. **存储**：将文本内容和向量分别存储到 MySQL 和 PostgreSQL 数据库

**（2）分块策略算法设计**

系统支持四种分块策略：

- **固定大小分块（fixed）**：按 500 字符固定大小分割，块间重叠 50 字符，尝试在句子边界截断
- **句子分块（sentence）**：按句子分隔符（。！？\n）分割，合并句子到不超过 500 字符的块中
- **段落分块（paragraph）**：按段落（\n\n）分割，合并段落到不超过 800 字符的块中
- **递归分块（recursive）**：使用多种分隔符（\n\n→\n→。！→？→；→，）递归分割，最小块大小 100 字符

**（3）向量化与存储流程**

分块完成后，系统执行以下步骤：

1. 将文本块批量发送给 DashScope API 获取向量
2. 将文本内容和向量插入 PostgreSQL 的 knowledge_vectors 表
3. 将关联数据插入 MySQL 的 nutrition_knowledge 和 knowledge_embeddings 表
4. 更新任务状态为完成

**（1）用户管理功能设计**

管理员可查看平台用户列表，包含用户 ID、用户名、邮箱、手机号和管理员标识。后续可扩展用户封禁、删除等管理功能。

#### 4.3.2 逻辑结构设计

系统数据库包含 MySQL 业务数据库中的 17 张表和 PostgreSQL 向量数据库中的 1 张表，共计 18 张表。各表通过外键约束和索引设计确保数据完整性和查询效率。

**主键/外键约束设计原则：**

- 所有表使用自增 BIGINT 作为主键
- 外键使用 `ON DELETE RESTRICT` 和 `ON UPDATE RESTRICT` 防止级联删除和更新
- 关键字段使用 NOT NULL 约束保证数据完整性
- 使用 utf8mb4 字符集支持完整的 Unicode 字符

#### 4.3.3 物理结构设计

**MySQL 数据库**

- 存储引擎：InnoDB，支持 ACID 事务和行级锁定
- 字符集：utf8mb4，支持完整 Unicode 字符集
- 排序规则：utf8mb4_unicode_ci

**PostgreSQL 数据库**

- 版本：PostgreSQL 14+
- 扩展：pgvector，提供向量数据类型和相似度搜索功能
- 向量存储方式：JSONB 格式存储 1024 维浮点向量
- 相似度度量：余弦距离（<=> 运算符）

**索引设计**

|------|------|---------|------|

**表 4.18 knowledge_vectors（向量知识表）**

| 字段名 | 数据类型 | 主键 | 外键 | 可为空 | 默认值 | 说明 |
|--------|---------|------|------|--------|--------|------|
| id | SERIAL | 是 | 否 | 否 | AUTO_INCREMENT | 记录ID |
| content | TEXT | 否 | 否 | 否 | - | 知识内容文本 |
| content_type | VARCHAR(50) | 否 | 否 | 是 | 'general' | 内容类型 |
| metadata | TEXT | 否 | 否 | 是 | NULL | 元数据（JSON格式） |
| embedding | TEXT | 否 | 否 | 是 | NULL | 1024维嵌入向量（JSON格式） |
| created_at | TIMESTAMP | 否 | 否 | 是 | CURRENT_TIMESTAMP | 创建时间 |

**表说明：**

PostgreSQL 中的 knowledge_vectors 表是向量知识库的核心存储表。该表使用 TEXT 类型存储 1024 维嵌入向量（JSON 格式），通过 PostgreSQL 的 JSONB 运算符实现余弦相似度搜索。系统在执行语义搜索时，使用以下 SQL 语句：

```sql
SELECT id, content, content_type, metadata, embedding,
       1 - ((embedding::jsonb) <=> (:embedding::jsonb)) as similarity
FROM knowledge_vectors
ORDER BY (embedding::jsonb) <=> (:embedding::jsonb)
LIMIT :top_k
```

其中 `<=>` 是 pgvector 扩展提供的余弦距离运算符，`1 - 距离` 即为余弦相似度。系统设置相似度阈值（如 0.8）来过滤不相关的检索结果。

### 4.5 安全设计

#### 4.5.1 认证安全

**（1）密码加密（bcrypt）**

系统使用 bcrypt 算法对用户密码进行哈希加密。bcrypt 是一种自适应的密码哈希函数，通过引入盐值（Salt）和工作因子（Work Factor）抵御彩虹表攻击和暴力破解。密码在注册时加密存储，登录时通过 bcrypt.checkpw 验证。

**（2）JWT Token 签发与验证**

JWT Token 包含用户 ID 和过期时间声明，使用 HS256 算法和配置的密钥进行签名。Token 签发后返回给客户端，客户端在后续请求中通过 Authorization: Bearer {token} 头部携带 Token。后端通过 verify_token 函数验证 Token 的有效性和完整性。

**（3）Token 过期与刷新机制**

Token 默认有效期为 24 小时。过期后用户需要重新登录获取新的 Token。系统可在未来扩展 Token 刷新机制，允许在 Token 即将过期时自动获取新 Token，提升用户体验。

#### 4.5.2 接口安全

**（1）CORS 跨域配置**

后端通过 CORSMiddleware 配置允许的跨域请求来源，默认允许所有来源（allow_origins=["*"]），在生产环境中应配置为具体的前端域名。

**（2）管理员权限拦截**

通过 FastAPI 的依赖注入机制，管理接口使用 require_admin 依赖函数验证管理员身份。该函数检查当前用户的 is_admin 字段，非管理员用户访问时将抛出 HTTPException(403, "需要管理员权限")。

**（3）输入数据验证**

所有 API 接口使用 Pydantic 模型进行请求数据验证，确保输入数据的类型、长度和格式符合要求。例如，密码长度限制为 6-50 字符，邮箱格式通过 EmailStr 自动校验，用户名/邮箱/手机号至少提供一种等。
