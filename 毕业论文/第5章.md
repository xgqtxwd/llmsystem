## 第 5 章 系统实现与测试

### 5.1 开发环境搭建

#### 5.1.1 后端环境

本系统后端基于 Python 3.10+ 开发，采用 Conda 虚拟环境（llmenv）进行依赖管理。核心框架为 FastAPI，数据库使用 MySQL 8.0+ 存储业务数据、PostgreSQL 14+ 配合 pgvector 扩展存储向量数据。通过 pip 安装所有依赖包，主要包括：

- FastAPI：异步 Web 框架
- SQLAlchemy：ORM 数据库操作
- Pydantic：数据验证与序列化
- bcrypt：密码加密
- python-jose：JWT Token 生成与验证
- httpx：异步 HTTP 客户端
- PyPDF2 / python-docx：文档解析

#### 5.1.2 前端环境

前端基于 Node.js 18+ 环境，使用 Vite 构建工具初始化 Vue 3 项目。核心依赖包括：

- Vue 3：渐进式 JavaScript 框架
- Vue Router：前端路由管理
- Pinia：全局状态管理
- Axios：HTTP 请求封装
- Vant 4：移动端 UI 组件库

### 5.2 后端核心功能实现

#### 5.2.1 用户认证功能实现

用户认证模块包含注册、登录、Token 刷新和登出四个核心接口。注册接口（POST /api/v1/auth/register）接收用户名、邮箱、手机号和密码，使用 Pydantic 模型进行数据校验，通过 bcrypt.hashpw() 对密码进行加密处理后写入 MySQL users 表。登录接口（POST /api/v1/auth/login）支持用户名、邮箱或手机号三种登录方式，验证通过后使用 python-jose 库生成 JWT Token，有效期为 24 小时。

权限中间件通过 get_current_user() 函数实现，在受保护的路由中自动解析 Authorization 请求头，验证 Token 有效性并注入当前用户对象。Token 刷新接口允许用户在 Token 即将过期时获取新的 Token，避免频繁重新登录。

#### 5.2.2 LLM 服务层实现

LLMService 类封装了大语言模型的调用逻辑。通过 httpx.AsyncClient 发起异步 HTTP 请求，调用豆包大模型 API（OpenAI 兼容接口）。核心方法 chat_completion() 接收消息列表、系统提示词、温度和最大 Token 数等参数，构建标准 OpenAI 格式的请求体，包含重试机制（最多 2 次）和超时处理（60 秒）。

系统内置两个业务方法：generate_nutrition_advice() 用于生成营养建议，根据用户健康档案和问题构建上下文；generate_recipe_recommendation() 用于生成食谱推荐，考虑用户的口味偏好、过敏食物和健康目标。_build_user_context() 方法将用户的年龄、性别、BMI、活动水平等信息格式化为自然语言上下文。

【表5.1 LLM 服务核心方法】

| 方法名 | 功能描述 | 参数 | 返回值 |
|--------|---------|------|--------|
| chat_completion() | 通用对话生成 | messages, system_prompt, temperature, max_tokens | Dict[success, content, usage] |
| generate_nutrition_advice() | 营养建议生成 | user_context, question | str (回答文本) |
| generate_recipe_recommendation() | 食谱推荐生成 | user_context, meal_type | str (食谱内容) |
| _build_user_context() | 构建用户上下文 | user_context | str (格式化文本) |

#### 5.2.3 RAG 服务层实现

RAGService 类实现检索增强生成（Retrieval-Augmented Generation）流程。初始化时连接向量数据库和嵌入服务，并自动填充默认营养知识（包括营养知识、食谱、食材、饮食建议和季节性知识共 25 条）。

核心方法 generate_recipe_with_rag() 的工作流程为：首先根据用户查询构建检索词，调用 retrieve_knowledge() 获取相似度最高的 5 条知识片段；然后将用户背景、可用食材、餐次类型和检索到的知识组装成 Prompt；最后调用豆包大模型生成个性化食谱。generate_nutrition_advice_with_rag() 同理，先检索相关知识再回答问题，确保回答基于权威知识而非模型幻觉。

retrieve_knowledge() 方法使用 EmbeddingService 将查询文本转换为 1024 维向量，在 PostgreSQL 的 knowledge_vectors 表中执行余弦相似度搜索，按相似度倒序返回 top_k 条结果。

#### 5.2.4 向量数据库操作实现

VectorDatabase 类封装了向量数据库的 CRUD 操作。底层使用 SQLAlchemy 引擎连接 PostgreSQL，通过原生 SQL 实现向量相似度搜索。insert_vector() 方法将内容、嵌入向量、内容类型和元数据插入 knowledge_vectors 表；search_similar() 方法使用 PostgreSQL 的 JSONB 操作符计算向量余弦距离（<=>），支持按内容类型过滤和分页查询；delete_vector() 和 update_metadata() 分别实现删除和更新操作。

EmbeddingService 类调用阿里云 DashScope 的 text-embedding-v4 模型获取文本嵌入向量，支持批量处理（最多 25 个文本/批次），输出 1024 维向量。get_embedding() 获取单个文本的向量，get_embeddings() 获取多个文本的向量列表。

#### 5.2.5 文档解析与入库实现

文档上传接口（POST /api/v1/admin/document/upload）支持 PDF、Word、TXT、Markdown 四种格式，文件大小限制为 30MB。文档解析阶段：PDF 使用 PyPDF2 的 PdfReader 逐页提取文本；Word 使用 python-docx 的 Document 提取段落文本；TXT 和 Markdown 直接读取 UTF-8 编码内容。

文本分块阶段提供四种策略：固定大小分块（500 字符/块，重叠 50 字符）、句子分块（按句号、感叹号、问号分割，合并到 ≤500 字符）、段落分块（按双换行分割，合并到 ≤800 字符）、递归分块（多级分隔符，最小 100 字符）。

【表5.2 文本分块策略对比】

| 分块策略 | 分隔符 | 块大小限制 | 重叠字符 | 适用场景 |
|---------|--------|-----------|---------|---------|
| fixed | 固定字符数 | 500 | 50 | 均匀分布内容 |
| sentence | 。！？\n | ≤500 | 无 | 保持语义完整 |
| paragraph | \n\n | ≤800 | 无 | 保留段落结构 |
| recursive | \n\n→\n→。！→？→；→， | 最小100 | 无 | 多层次分割 |

后台采用异步任务处理机制，批量向量化（每批 5 个文本块）并存储到双数据库（PostgreSQL 和 MySQL）。任务状态通过全局字典 upload_tasks 跟踪，支持前端轮询查询进度。

#### 5.2.6 食谱推荐功能实现

AI 推荐接口（POST /api/v1/recipes/ai-recommend）接收用户的饮食偏好和已有食材列表，首先获取用户的健康档案、饮食偏好和健康目标，然后调用 RAG 服务生成个性化食谱。季节性推荐接口（GET /api/v1/recipes/seasonal）根据当前月份自动判断季节，检索对应的季节性饮食建议。食材替代接口（POST /api/v1/recipes/substitute）接收目标食材，由 LLM 生成多种替代方案。

#### 5.2.7 食材识别功能实现

食材识别支持文件上传和 URL 两种方式。文件上传接口（POST /api/v1/recipes/recognize）接收 JPG、PNG、GIF、WEBP 格式图片，读取文件内容并进行 Base64 编码，调用 VisionService.analyze_image_base64() 方法。URL 识别接口（GET /api/v1/recipes/recognize-url）接收图片 URL，调用 VisionService.analyze_image() 方法。

VisionService 使用 DashScope 的 qwen-vl-plus 多模态视觉语言模型，请求内容包括图片和系统提示词（"请识别图片中的食材，并给出每种食材的营养信息"）。识别结果写入 food_recognition_records 表，返回格式化的食材列表和营养信息。

#### 5.2.8 知识库查询功能实现

知识查询接口（GET /api/v1/knowledge）支持传统数据库知识和向量知识库的融合查询。传统知识从 MySQL 的 nutrition_knowledge 表分页查询，支持按分类筛选；向量知识调用 RAG 服务的 retrieve_knowledge() 进行语义搜索。双源知识合并后统一返回，并通过 is_vector 字段标识来源。

#### 5.3.1 前端项目架构

项目采用 Vue 3 Composition API，使用 script setup 语法。路由配置通过 Vue Router 实现，包含首页、营养咨询、食谱推荐、营养知识、个人中心等页面。Pinia 状态管理维护用户认证信息，通过 authStore 实现登录状态持久化。Axios 请求封装在 api/index.js 中，自动添加 Authorization 请求头，统一处理 401 和 500 错误。

### 5.4 关键技术与难点解决方案

#### 5.4.1 RAG 检索精度优化

初期使用固定相似度阈值导致部分不相关知识被检索。通过调整 top_k 参数（从 10 优化到 5）和引入相关性过滤策略，提高检索精度。在 Prompt 中加入检索到的知识片段，并标注相似度分数，使模型能够区分相关知识与噪声。

#### 5.4.2 文档解析耗时问题

【图5.8 文档解析进度展示】

文档向量化过程耗时较长（通常数分钟），初始方案使用同步请求导致前端超时。解决方案：后端将向量化改为后台异步任务，前端上传后立即返回 task_id，通过轮询接口（GET /api/v1/admin/document/status）每 2 秒查询进度。前端使用 localStorage 持久化任务数据，防止页面刷新或切换导致进度丢失。任务分为四个阶段：解析文档（15%）、文本分块（30%）、向量化处理（60%）、存储完成（100%），每个阶段显示详细指标。

#### 5.4.3 多源知识融合展示

传统知识库（MySQL）和向量知识库（PostgreSQL）数据结构不同，需统一展示。解决方案：设计统一的数据传输模型 KnowledgeItem，包含公共字段（id、content、category）和扩展字段（is_vector、similarity、metadata）。前端根据 is_vector 字段区分显示样式，向量知识使用金色边框和"文档入库"标识。搜索时同时查询两种数据源，合并结果按相关度排序。
